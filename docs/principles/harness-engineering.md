# Harness Engineering 实践

> 来源：Harness Engineering实践 + 你不知道的 Agent：原理、架构与工程实践
> 核心结论：**Harness > 模型**——稳定性由外围工程决定，而非模型能力。

## 1. 什么是 Harness

Harness 是围绕 Agent 构建的测试、验证与约束基础设施，至少包括四个部分：

| 组件 | 作用 |
|------|------|
| 验收基线 | 定义"成功"的机器可执行标准 |
| 执行边界 | 沙箱、权限、资源限制 |
| 反馈信号 | 追踪、指标、事件流 |
| 回退手段 | 压缩、回滚、降级 |

## 2. Harness 比模型更关键

**核心判断**：模型虽然重要，但决定系统能不能稳定运行的，往往是外围工程条件。

OpenAI 的 Agent 优先开发实践证明了这一点：3 个工程师 5 个月写了百万行代码，速度是传统开发的 10 倍。关键决策：

1. **知识必须存在于代码库本身**：外部文档对运行中的 Agent 不可见，`AGENTS.md` 只保留约 100 行作为索引
2. **约束编码化而非文档化**：写在文档里的规范容易被忽略，编码进 Linter、类型系统或 CI 规则里的约束才具备可执行性
3. **Agent 端到端自主完成任务**：从验证当前状态到开 PR、处理 Review 反馈、自主合并，全链路不需要人介入
4. **最小化合并阻力**：从人工 Review 变成机器执行的约束，一次写进去，到处生效

## 3. Agent Loop 基本运转

核心循环（感知 → 决策 → 行动 → 反馈）：

```
while (true):
  response = model(messages, tools)
  if stop_reason == "tool_use":
    results = execute_tools(response.tool_calls)
    messages += [response, results]
  else:
    return response.text
```

**关键原则**：循环本身保持稳定，新能力通过三种方式接入：
- 扩展工具集和 handler
- 调整系统提示结构
- 把状态外化到文件或数据库

不应该让循环体本身变成一个巨大的状态机。模型负责推理，外部系统负责状态和边界。

## 4. Workflow vs Agent

| 维度 | Workflow | Agent |
|------|----------|-------|
| 控制权 | 代码预定义 | LLM 动态决策 |
| 执行方式 | 工具顺序固定 | 工具按需选择 |
| 状态与记忆 | 显式状态机 | 隐式上下文 |
| 可观测性 | 日志定位节点 | 需完整执行记录 |
| 适用场景 | 流程固定、输入清晰 | 需要中间推理与灵活判断 |

## 4. 五种常见控制模式

1. **Prompt Chaining**：任务拆成顺序步骤，每步 LLM 处理上一步的输出
2. **Routing**：对输入分类，定向到对应的专用处理流程
3. **Parallelization**：分段法（独立子任务并发）或投票法（同一任务跑多次取共识）
4. **Orchestrator-Workers**：中央 LLM 动态分解任务，委派给工作者 LLM
5. **Evaluator-Optimizer**：生成器产出，评估器给反馈，循环直到达标

## 5. 任务清晰度矩阵

```
         验证自动化程度
         高          低
任务  高  [最适合Agent]  [人盯验收]
清晰度
    低  [高效但危险]    [Agent无效]
```

Harness 要做的就是把任务推进右上角——让对错有机器可以执行的判断标准，而不是靠人盯。

## 6. 评测优先原则

- **第一个失败 = 第一个测试用例**
- 评测系统本身的问题，比 Agent 出问题更难发现
- 如果一直在 Agent 代码上反复调，效果未必明显——先检查评测系统
- 三种评测器形成级联：L1 确定性 → L2 启发式 → L3 LLM-as-Judge
